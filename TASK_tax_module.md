# ЗАВДАННЯ: Модуль податкового обліку (юрособи, доходи, ліміти, податки, чернетки звітів)

Ти працюєш у наявному production-проекті — CRM/адмінпанелі для e-commerce (мульти-магазини, замовлення, оплати, закупівлі, виробництво, рольова модель доступу, генерація поштових декларацій, інтеграції оплат, автоматична обробка банківських виписок).

**Мета модуля:** додати в адмінку облік юридичних осіб (ФОП / ТОВ), визнання доходу на основі наявних даних про оплати та банківські виписки, контроль лімітів єдиного податку, розрахунок податків (ЄП, ЄСВ, військовий збір) і формування чернеток звітів для податкової.

---

## Відомий контекст: наявна структура оплат (підтверджено користувачем)

У проекті вже є універсальна платіжна модель — врахуй її як даність, актуальну версію звір з кодом і PlantUML-діаграмами в репозиторії:

- **`Payment`** — джерело правди про фінансові операції. `direction` (`incoming`/`outgoing`), `type` (`cash`/`card`/`bank_transfer`/`online`/`other`), `amount` у валюті платежу + `amountBase` у `Store.baseCurrency` за снапшотом `exchangeRateToBase`, `paidAt`, зв'язок рівно з одним з: `order` (зазвичай incoming) або `purchase` (зазвичай outgoing), `reversesPayment` (реверс із протилежним `direction` і причиною в `comment`), `store`, `externalReference`, аудит-поля (`createdBy`/`updatedBy`, `version`).
- **`PaymentHistory`** — append-only фід/таймлайн платіжних подій (`payment.recorded`, `payment.reversed`), денормалізований, без backfill старих записів. **Це шар відображення/аудиту, а НЕ фінансове джерело — для податкового модуля джерелом даних не використовувати.**
- `Order.paidAmountBase` / `Purchase.paidAmountBase` / `paymentStatus` — денормалізований кеш, перераховується з `Payment`. Теж не джерело для податків.
- Грошова конвенція проекту: `decimal(14,4)`, курси — `decimal(18,8)`, дати — `DateTimeImmutable`.

## 0. Правила виконання (читати перед стартом, дотримуватись завжди)

1. **Поетапність.** Виконуй фази строго по черзі (Фаза 0 → 6). Після кожної фази: прогнати тести, зробити окремий commit з префіксом `tax-module: phase N — ...`, вивести короткий підсумок (що зроблено, що відкладено, відкриті питання) і **зупинитися та чекати підтвердження** перед наступною фазою.
2. **Спочатку дослідження, потім код.** Жодних міграцій і коду до завершення Фази 0 та погодження плану.
3. **Конвенції проекту понад усе.** Іменування таблиць/полів, стиль міграцій, структура API, UI-компоненти, валідація, локалізація — все має відповідати тому, що вже є в проекті. Якщо в цьому завданні назва сутності конфліктує з конвенціями проекту — адаптуй назву, не ламай конвенцію.
4. **Не чіпати наявну логіку оплат і виписок деструктивно.** Інтеграція — через нові таблиці, події/хуки або read-only вибірки. Якщо без зміни наявного коду не обійтись — мінімальна зміна, окремо описана в підсумку фази.
5. **Гроші — за конвенцією проекту.** Суми — `decimal(14,4)`, курси — `decimal(18,8)`, патерн «`amount` у валюті операції + гривневий еквівалент окремим полем зі снапшотом курсу», як у `Payment`. Жодних float. Якщо в проекті є хелпери/value object для грошей — використовуй їх.
6. **Жодних захардкоджених ставок і лімітів у коді.** Усі ставки, ліміти, МЗП, прожитковий мінімум — лише з довідкової таблиці, версійованої по роках (див. Фазу 1 і розділ 11).
7. **Міграції мають бути зворотними** (down/rollback), без втрати наявних даних.
8. **Аудит.** Будь-яка ручна зміна класифікації доходу чи статусу періоду — з фіксацією хто/коли/що змінив (використай наявний механізм аудиту, якщо він є).
9. **Дисклеймер.** Модуль — інструмент обліку, а не податкова консультація. Всі цифри в seed позначай як такі, що потребують перевірки користувачем (розділ 11).

## Фаза 1 — Модель даних і міграції

Створи міграції та сутності за конвенціями проекту: ті самі аудит-поля, що в `Payment` (`version`, `createdAt`/`updatedAt`, `createdBy`/`updatedBy` де доречно), суми `decimal(14,4)`, курси `decimal(18,8)`, enum-и в стилі наявних (`PaymentDirectionEnum` тощо). Орієнтовні назви (фіналізуй у Фазі 0):

1. **`LegalEntity`** — юрособи:
   - назва (повна і коротка), тип (`fop` | `tov`);
   - податковий номер (РНОКПП для ФОП / ЄДРПОУ для ТОВ);
   - система оподаткування (`simplified` | `general`), група ЄП (1 | 2 | 3 | null), ставка ЄП для 3 групи (5% / 3%), ознака платника ПДВ, прапорець звільнення від ЄСВ;
   - дата реєстрації / переходу на спрощену систему, статус (active/closed), адреса, КВЕДи;
   - зв'язок з розрахунковими рахунками — згідно з тим, як рахунки змодельовані в банківському модулі (Фаза 0).
2. **`Store.legalEntity`** — nullable FK на `LegalEntity` (мінімальна зміна наявної сутності `Store`, окремо описати в підсумку фази). Після заповнення для всіх магазинів — джерело мапінгу «оплата → юрособа» через `Payment.store`. Кардинальність (чи може магазин працювати від кількох юросіб у часі) — за рішенням Фази 0; якщо так — таблиця прив'язки з датами діії замість простого FK.
3. **`TaxRateSet`** — довідник показників, версійований по роках: рік, МЗП на 1 січня, прожитковий мінімум, ліміти доходу по групах, фіксовані ставки ЄП (гр. 1–2), відсоткові ставки ЄП (гр. 3, з/без ПДВ), ставка та база ЄСВ, ставки ВЗ по групах. Seed на 2026 рік — значення з розділу 11, з коментарем «перевірити актуальність».
4. **`IncomeRecord`** — визнаний дохід (append-only проєкція):
   - `legalEntity` — **снапшот на момент визнання** (не обчислювати через `Payment.store → Store.legalEntity` на льоту: прив'язка магазину може змінитися, а визнаний дохід — ні); `store` — довідково;
   - `recognizedAt` (дата визнання), `amount` + `currency` як у джерелі, **`amountUah`** + `nbuExchangeRate` (для UAH: `amountUah = amount`, курс 1). Увага: `Payment.amountBase` — у `Store.baseCurrency` за комерційним снапшотом курсу, для податку придатний лише якщо базова валюта UAH і платіж гривневий;
   - джерело: `sourceType` (`payment` | `bank_statement_row` | `manual`) + `sourceId`, **unique (`sourceType`, `sourceId`)** — захист від задвоєння; для зручності — пряма nullable FK на `Payment`;
   - класифікація (`income` | `refund` | `non_income_transfer` | `non_income_own_funds` | `non_income_other`), контрагент, призначення платежу, коментар;
   - хто/коли створив і змінював класифікацію.
5. **`TaxReportingPeriod`** — звітні періоди: юрособа, тип (місяць/квартал/рік), межі періоду, статус (`open` | `closed` | `declared`).
6. **`TaxAccrual`** — нарахування/сплати: юрособа, період, тип податку (`ep` | `esv` | `vz`), нараховано, сплачено, дедлайн сплати, дата сплати, статус, опційне посилання на рядок виписки, яким сплачено.
7. **`TaxReportDraft`** — чернетки звітів: юрособа, період, тип звіту, версія форми, payload (json з усіма полями звіту), дата генерації, статус (`draft` | `exported`).

Індекси: мінімум `(legalEntity, recognizedAt)` та `(legalEntity, classification, recognizedAt)` на `IncomeRecord`, по періодах/дедлайнах на `TaxAccrual`. CRUD юросіб в адмінці (форма + список) у стилі наявних розділів. **PlantUML-діаграма** нових сутностей `Shop database - Tax` у тому самому каталозі і стилі, що наявні діаграми (з `!include ./_common.puml`), включно з нотами про правила мапінгу з `Payment`.

**Критерії приймання:** міграції накатуються і відкочуються; можна створити ФОП 3 групи і ТОВ та прив'язати магазини; довідник 2026 засіяний; CRUD юросіб працює і закритий правами (тимчасово — наявною адмін-роллю, фінальні права у Фазі 6); діаграма додана.

## Фаза 2 — Визнання доходу: проєкція з Payment + виписки

Для ФОП на ЄП діє **касовий метод**: дохід визнається на дату фактичного надходження коштів на рахунок/в касу, наростаючим підсумком з 1 січня.

**Джерела `IncomeRecord`, за пріоритетом:**

1. **`Payment` — основне джерело.** Правила мапінгу:
   - `direction = incoming` (зазвичай прив'язаний до `order`) → кандидат у дохід; дата визнання — `paidAt` (з урахуванням рішення про еквайринг нижче); сума — `amount`/`currency`;
   - реверс (`reversesPayment` заповнено, протилежний `direction`) → запис `refund`, що **зменшує дохід у періоді повернення**, а не в періоді первинної оплати; зв'язок з оригінальним записом доходу зберегти;
   - `direction = outgoing` з `purchase` → не дохід, ігнорувати (витрати на ЄП на базу не впливають);
   - `type = cash` → готівкова виручка, включається в дохід;
   - **синхронізація без зміни ядра платіжного модуля:** доменна подія / ORM-лістенер на створення `Payment` і реверсу → створення `IncomeRecord` з автокласифікацією; ідемпотентність гарантована unique (`sourceType`, `sourceId`);
   - **`PaymentHistory` джерелом не використовувати** — це фід для таймлайну без backfill, фінансове джерело правди — `Payment`.
2. **Рядки банківських виписок, що не стали `Payment`** (Фаза 0 має підтвердити, де вони живуть): конфігуровані правила автокласифікації (рахунок, ЄДРПОУ контрагента, шаблон призначення платежу) → дохід / не дохід / повернення. Типові «не дохід»: поповнення власних коштів, перекази між власними рахунками однієї юрособи, кредитні кошти, помилкові зарахування. Подбати, щоб надходження, яке існує і як `Payment`, і як рядок виписки, не стало двома записами доходу (правило дедуплікації — за рішенням Фази 0, наприклад пріоритет `Payment` + матчинг по `externalReference`).
3. **Ручні записи** — для доходу поза системою.

**Рішення про еквайринг (зафіксувати у плані Фази 0, параметризувати per `PaymentType`):** для `card`/`online` податковий дохід виникає на дату зарахування коштів на рахунок і в **повній сумі оплати до утримання комісії еквайра**. Якщо `paidAt` — дата оплати покупцем, а не дата зарахування, MVP може визнавати по `paidAt` як свідоме задокументоване спрощення (лаг 1–3 дні, критично лише на межі кварталу/року, консервативно — дохід визнається раніше) — але це має бути явний конфіг, а сума — завжди повна, не «за мінусом комісії».

**Валюта:** `amountBase` у `Store.baseCurrency` за комерційним снапшотом курсу для податку не годиться. Для валютних надходжень `IncomeRecord.amountUah` рахується за курсом НБУ на дату визнання (джерело курсів НБУ — за рішенням Фази 0). Якщо валютних надходжень у системі немає — логіку відкласти, структуру залишити готовою.

**Також у цій фазі:**
- ручна перекласифікація в UI (зі сторінки доходів і з картки оплати/рядка виписки) з аудит-логом;
- **backfill-команда** для історичних `Payment` (і рядків виписок, якщо актуально): обов'язковий `--dry-run` зі звітом — кількість записів, розподіл за класифікацією, сумарний дохід по юрособах і роках — перед реальним записом;
- сторінка «Доходи» по юрособі: фільтри за періодом/класифікацією/джерелом/магазином, підсумки, додавання ручного запису.

**Критерії приймання:** dry-run по реальних історичних `Payment` дає суми по роках, які користувач підтверджує як правдоподібні; реверс зменшує дохід у своєму періоді; задвоєння неможливе (включно з кейсом «Payment + той самий рядок виписки»); нові оплати підхоплюються автоматично; поведінка платіжного модуля не змінена.

## Фаза 3 — Контроль ліміту і дашборд

1. **Розрахунок доходу наростаючим підсумком** за календарний рік по кожній юрособі (тільки записи з класифікацією «дохід» мінус «повернення»).
2. **Порівняння з лімітом** групи з довідника поточного року: прогрес-бар, абсолютні суми («використано / залишок»), відсоток.
3. **Пороги попереджень** (конфігуровані, дефолт 70% / 85% / 95%): візуальна індикація + нотифікація через наявний механізм (якщо механізму немає — банер в адмінці, нотифікації окремим питанням).
4. **Прогноз:** середньоденний дохід за останні 30/90 днів × дні до кінця року = очікуваний річний дохід; прогнозована дата досягнення ліміту.
5. **Віджет на головному дашборді** (стисло: юрособа, % ліміту, статус) + окрема сторінка «Податковий контроль» з деталізацією по місяцях/кварталах.

**Критерії приймання:** суми збігаються зі сторінкою «Доходи»; пороги спрацьовують; прогноз перераховується щодня (фонова задача або обчислення на льоту — за конвенціями проекту).

## Фаза 4 — Розрахунок податків і календар платежів

Усі формули беруть значення лише з `tax_reference_rates` відповідного року.

1. **Єдиний податок:**
   - група 3: ставка (5% без ПДВ / 3% з ПДВ) × дохід за квартал; сплата щоквартально;
   - групи 1–2: фіксована сума щомісяця (аванс до 20 числа включно).
2. **ЄСВ «за себе»:** мінімум 22% МЗП за кожен місяць; сплата щоквартально до 20 числа місяця після кварталу. Передбач прапорець звільнення від ЄСВ (наприклад, ФОП одночасно є найманим працівником або має пільгу) на рівні юрособи.
3. **Військовий збір:** група 3 — 1% доходу за квартал (строки як для ЄП); групи 1–2 — 10% МЗП щомісяця (аванс до 20 числа).
4. **Календар платежів:** автогенерація `tax_accruals` з дедлайнами по періодах; статуси «нараховано / сплачено / прострочено»; нагадування за N днів до дедлайну.
5. **Звірка сплат з виписками (nice to have):** сплати податків не потрапляють у `Payment` (він вимагає `order` або `purchase`), тож шукати їх серед вихідних рядків банківських виписок: зіставлення за ЄДРПОУ отримувача (Казначейство) / призначенням платежу з нарахуваннями — пропозиція «відмітити як сплачено» з підтвердженням користувача.
6. ТОВ на загальній системі: розрахунок податку на прибуток і облік ПДВ **поза скоупом MVP** — структура даних має це дозволяти в майбутньому, але формули не реалізовуємо (див. розділ 10).

**Критерії приймання:** юніт-тести на кожну формулу, включно з округленнями (правила округлення — до копійки, зафіксувати в тестах) і межовими кейсами (нульовий дохід, реєстрація ФОП всередині року, зміна групи всередині року — мінімум коректне розбиття періодів).

## Фаза 5 — Чернетки звітів

1. **Декларація платника єдиного податку ФОП:** квартальна (наростаючим підсумком) для 3 групи, річна для 1–2 груп, з додатком 1 (ЄСВ). Перед реалізацією **перевір актуальну форму** (станом на 2025–2026 діє форма за наказом Мінфіну від 31.01.2025 № 57 — верифікувати) і зафіксуй версію форми в `tax_report_drafts`.
2. **Генерація чернетки:** збирання всіх полів форми з даних модуля в payload; сторінка перегляду з можливістю ручного коригування окремих полів перед експортом (коригування зберігаються в payload з позначкою «manual»).
3. **Експорт:** друкована форма (HTML → PDF за наявним у проекті механізмом генерації документів) з помітним водяним знаком/написом «ЧЕРНЕТКА — перевірити перед поданням».
4. **XML для Електронного кабінету — опційно, experimental:** реалізуй лише якщо вдасться надійно верифікувати актуальний код форми та XSD; інакше — залиш задокументований TODO. Не вгадуй структуру XML.
5. В UI модуля — постійний дисклеймер: «Розрахунки довідкові, не є податковою консультацією; перевіряйте суми та форми перед поданням».

**Критерії приймання:** чернетка за тестовий квартал збігається з ручним розрахунком на тих самих даних; PDF генерується; закриття періоду (`closed` → `declared`) блокує зміну доходів у ньому (зі шляхом «переввідкрити» для виправлень, з аудитом).

## Фаза 6 — Права доступу, тести, документація

1. **RBAC:** нові пермішени за конвенціями проекту, орієнтовно `tax.view`, `tax.income.manage`, `tax.reports.manage`, `tax.settings.manage` (довідник ставок, правила класифікації). Призначити дефолтним ролям розумні значення, фінансові дані не показувати ролям без прав.
2. **Тести:** юніт (формули, класифікація, ліміти/пороги, округлення), інтеграційні (backfill dry-run, генерація чернетки, закриття періоду). Прогнати весь наявний тест-сьют проекту — нічого не зламано.
3. **Документація:** `docs/tax-module/README.md` (архітектура, таблиці, точки інтеграції, як додати ставки наступного року) + коротка інструкція користувача (як завести юрособу, перевірити класифікацію, сформувати чернетку).
4. Оновити `CLAUDE.md` проекту згадкою про модуль (якщо файл існує).

## 12. Definition of Done

Модуль вважається готовим, коли: всі фази закриті й закомічені окремо; для реальної юрособи користувача видно дохід наростаючим підсумком, % ліміту з прогнозом, нараховані ЄП/ЄСВ/ВЗ з дедлайнами; згенеровано коректну PDF-чернетку декларації за останній закритий квартал; тести зелені; документація на місці; жодна наявна функціональність (оплати, виписки, замовлення) не змінила поведінку.
